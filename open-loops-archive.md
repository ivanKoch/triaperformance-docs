- [x] ~~**`gbp_keywords` writes with a bare `DELETE`, and an empty fetch destroys the month.**~~ *(Found August 31, 2026, while checking why one of eight sources returned zero rows on an otherwise clean run. **The zero itself is almost certainly real** — not a defect, and worth saying first.)*
  **Why the zero is not the finding:** `gbp_search_keywords` holds 13 months back to 2025-03 with **0–7 keywords a month**, and `sum(value)` is NULL for six of them — every row thresholded, i.e. Google returning «fewer than N» rather than a count. *2025-12, 2026-02, 2026-03 and 2026-06 are absent entirely.* **On a profile doing 60–96 views a month, a month with no keywords is ordinary.** *Do not re-raise the zero as a bug.*
  🚨 **The finding is the write path.** *`sync_gbp_data.py` runs `DELETE FROM gbp_search_keywords WHERE location_id=%s AND month=%s` unconditionally, then `INSERT`s only `if krows`.* **So a month that returns empty is deleted and replaced with nothing — an empty API response silently destroys stored data.** *This is the exact inverse of the bug fixed the day before on the GA4 side («an upsert cannot REMOVE a row that should no longer exist», resolved by DELETE-window-then-INSERT). **The same session that made writes destructive on purpose in one script left them destructive by accident in another.***
  **The second-order half, and it is the one that is probably already costing data.** *The daily window is a rolling ~7 days, so the loop can only ever reach the current month. Once the window clears the last day of a month — around the 8th — **that month is frozen at whatever incomplete state it was in**, and Google publishes monthly keyword data* ***after*** *the month closes.* **The rolling-window pattern is correct for GSC, which revises recent days, and wrong here, where the source publishes late rather than revising.** *A monthly source needs a monthly re-fetch of the closed month, not a daily re-fetch of the open one.*
  **Suggested fix, one line each:** guard the `DELETE` on `if krows`, and widen the keyword loop to re-fetch the previous month as well as the current one. *Small; the reason to log it rather than do it in passing is that it changes what a green `ok` row means, and this table's whole purpose is that a zero can be trusted.*

  ***Update, August 31, 2026 — BOTH HALVES FIXED IN THE REPO. Not closed: it closes when Iván runs it on the box and reports what the table holds.*** *Done ahead of close #1 deliberately — a close is the first consumer that quotes these numbers outside this repo, and a wrong number that has been published is a different problem from one that has not.*
  **It came out larger than "one line each", and the extra was worth it:**
  - **The empty fetch never deletes**, and the two empty cases are now separated. *Empty with no prior rows is unremarkable and is what Aug 31 returned; empty **with** prior rows keeps the stored rows and **names the month** in `analytics_sync_log.detail`.*
  - **`status` gains a third value, `partial`.** *A run that kept rows because it had nothing better is neither a success nor a failure, and* ***collapsing it into either one is how this bug stayed invisible for as long as it did*** *— it recorded `ok` every night while deleting data.*
  - **The window fix is the half that was already costing data**, and it reframes the defect: *`start` is `latest − 7 days`, correct for daily metrics and wrong for keywords, because* **GSC and the daily metrics *revise* recent days while GBP keywords are *published late*.** *A rolling 7-day window stops reaching a month around the 8th, so each month froze at whatever partial state it held when the window left it.* ***That is the likeliest explanation for the four months missing entirely (2025-12, 2026-02, 2026-03, 2026-06) — not that Google had nothing, but that nothing went back to ask after it did.*** The loop now reaches the **first of the previous month**.
  ***The two fixes turned out to be one fix, and the ordering is the finding.*** *Re-reading a closed month would have been actively dangerous under the old write path — a late re-fetch returning empty would have erased a month that was previously correct.* **The guard is what makes the wider window safe; the wider window is what makes the guard worth having.**

- [x] ~~**Two bugs on the coaching-token insert that have been cancelling each other out.**~~ **CLOSED August 20, 2026 — both, confirmed live. Closing note at the end; the original item follows so the reasoning survives.** *(Found Aug 10, 2026, chasing the cosmetic one.)*
  **(a) The dangerous one — `NULLIF` into a `NOT NULL` column.** `Insert Coaching Token in Postgres` writes `VALUES ($1, $2, $3, NULLIF($4, 'UNKNOWN'), TRUE)` against `preferred_language TEXT NOT NULL DEFAULT 'SPANISH'`. If `$4` ever genuinely equals `UNKNOWN`, `NULLIF` yields NULL, the insert violates the constraint, and a new coaching athlete ends up with a Twenty record and a welcome email but **no members-area token**. **The `DEFAULT` does not rescue it** — a default applies only when the column is *absent* from the INSERT, never when it is present and NULL. **This is the same trap already written down in `ai-infrastructure-documentation.md` §21** from the intake pipeline, hit a second time in a different workflow, which is the argument for treating it as a rule rather than an anecdote.
  **(b) The cosmetic one that has been hiding it.** Every value reaching that node has arrived as `=UNKNOWN` — n8n's expression prefix leaking into a literal — which is not equal to `'UNKNOWN'`, so `NULLIF` passed it through untouched. Fix either bug alone and the failure in (a) appears for the first time. Fix (a) first.
  **Fix for (a):** `COALESCE(NULLIF($4, 'UNKNOWN'), 'SPANISH')`, which makes the database agree with the Spanish-fallback decision already implemented in `Build Welcome Email` (Iván's call, Aug 8). Apply the same to `Insert Token in Postgres` (All-Access), which has a bare `$4` and would store a literal `UNKNOWN`.
  **Fix for (b):** the repo's reference copy of the node is clean, so **the live workflow has drifted from it** and the source can't be identified from the repo. Bisect with one run: trigger a coaching signup for a person with no `preferredLanguage` in Twenty and read the output of `Coaching Athlete Upserted` — `=UNKNOWN` there means it's that Set node's value field; plain `UNKNOWN` there means the `=` is introduced at the Postgres node's `queryReplacement`.

  ***Update, August 12, 2026 — repo side done, n8n side is Iván's. And the fix changed shape.*** *Both nodes in `automation/subscription-lifecycle-automation.json` now read `CASE WHEN $4 IN ('SPANISH', 'ENGLISH', 'PORTUGUESE') THEN $4 ELSE 'SPANISH' END`, **not** the `COALESCE(NULLIF($4,'UNKNOWN'), 'SPANISH')` prescribed above. `COALESCE(NULLIF(...))` blacklists one known-bad string: it would have caught `'UNKNOWN'` and passed `=UNKNOWN` — the value actually arriving — straight through. A whitelist accepts the three values that exist and sends everything else to Spanish, which is also what `auth_service/app.py` already does on read; previously the column and the code disagreed about what an unrecognised language means. **Generalised in `ai-infrastructure-documentation.md` §21: a sentinel value only works if you control every producer of that field — and the `=` leak proves we don't.** The infra doc's original §21 entry recorded the `NULLIF` sentinel as the fix, so it was teaching the bug; corrected in place. **Still needs Iván to paste both node changes into the n8n UI — the repo copy is documentation, not the source.***

  ***CONFIRMED LIVE, August 12, 2026 — (b) is not cosmetic. It is a language-routing bug affecting every non-Spanish coaching athlete, and it is now the highest-priority item on this branch.*** *Two-run test, pinned trigger data, real execution.*
  ***Run 1*** *(person absent from Twenty → expression falls back to `'UNKNOWN'`): the Telegram printed `Idioma: =UNKNOWN`. The template is `preferredLanguage === 'UNKNOWN' ? 'FALTA…' : preferredLanguage`, so printing the raw value **proves the strict comparison failed** — the value is `'=UNKNOWN'`, not `'UNKNOWN'`.*
  ***Run 2*** *(same person, `preferredLanguage` set to `ENGLISH` in Twenty by hand first): `Check Existing Person (Coaching)` returned `"preferredLanguage": "ENGLISH"` — confirmed in the node output — and the row written to `subscriber_tokens` came out **`SPANISH`**. **The `=` leaks on real values, not only on the `UNKNOWN` fallback.***
  ***The source is `Coaching Athlete Upserted`, assignment #3, and nothing else.*** *The decisive evidence is in the same Telegram message: `Lead source:` printed `FALTA -- ponelo en Twenty`, which requires `leadSourceExisting === 'UNKNOWN'` to be **true**. Assignments #3 and #4 sit in the same Set node and are written in identical syntax — #3 is corrupted, #4 is clean. So this is not n8n-wide behaviour and not the Postgres node's `queryReplacement`; it is one field's stored value, almost certainly beginning `==` (n8n strips the first `=` as the expression marker and the second survives into the output as a literal).*
  ***Blast radius is wider than the members-area URL.*** *`Build Welcome Email` reads the same field, so an English or Portuguese coaching athlete has been getting **the Spanish welcome email** as well as the Spanish members home. Likely near-zero in practice — there have been no coaching signups through this workflow since it went live July 24, and Tischhauser's ENGLISH token came from the July 25 backfill script, not from here — but that must be **verified by query, not assumed**, and the verification is logged below rather than performed.*

Before today the column would have held `=ENGLISH`, which is visibly broken; now it holds `SPANISH`, which looks deliberate. **That is a good trade for safety and a bad one for detectability, and it is only acceptable because the root cause is being fixed in the same session.** If the Set node is not fixed, remove the whitelist — a wrong value you can see beats a wrong value you cannot.*

If the `=` prefix leaks on **all** values rather than only on `UNKNOWN`, a real English coaching athlete arrives as `=ENGLISH`, matches nothing, and is routed to the Spanish members home — silently, with no error, both before and after today's whitelist.
