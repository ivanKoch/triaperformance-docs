## Notable engineering problems solved (Hermes setup era, July 2026)

Numbering preserved — other docs reference these by number (e.g. "Problem #7").

1. **Split-brain agent.** The Hermes Desktop App runs its own independent local agent by default. Early on, the desktop app was configured with one model provider (a free NVIDIA model) while the VPS ran a separate instance on Gemini — two disconnected "brains" with no shared memory. Diagnosed by checking the Desktop App's Gateway settings (confirmed "Local gateway" was selected, not "Remote") and resolved by explicitly connecting the Desktop App to the VPS as a remote backend.

2. **Managed hosting product too restrictive.** The first VPS attempt used Hostinger's "Managed Hermes" product. It provided no IP address, no root access, no exposed ports, and its Docker container's web terminal was a restricted shell (`lshell`) that blocked even basic commands like `curl`. After confirming (via the product's own official documentation) that its architecture doesn't support external application connections at all, the decision was made to provision a plain, self-managed VPS instead — more setup work up front, but removes a structural ceiling that would also have blocked website hosting and workflow automation later.

3. **Docker networking — dashboard unreachable despite looking correctly configured.** After starting the dashboard container with a port mapping (`-p 9119:9119`), it was still unreachable from outside. Root cause, found via `docker logs`: the application inside the container was binding to `127.0.0.1` (loopback-only) by default, which Docker's port mapping cannot forward external traffic to regardless of the `-p` flag. Fixed by explicitly passing `--host 0.0.0.0` to the dashboard process.

4. **OAuth redirect mismatch.** Registering the dashboard for Nous Portal OAuth login through the web UI (rather than the CLI) only allowlisted `localhost`/`127.0.0.1` as valid callback addresses by default. Attempting to sign in via the VPS's public IP failed with `redirect_uri_mismatch`. Rather than provisioning a domain name and TLS certificate purely to satisfy the OAuth callback requirement, the simpler and more appropriate fix for a single-user system was adopted: Tailscale VPN + username/password auth.

5. **Docker-in-Docker terminal sandbox failure.** The setup wizard's "Docker" terminal-backend option (intended to sandbox agent-executed commands in nested containers) failed because the outer Hermes container had no access to the host's Docker daemon. Rather than mount the host's Docker socket into the container to fix this (a change that would reduce isolation, since socket access is equivalent to host root), the terminal backend was switched to `local`, relying on the existing outer-container boundary instead.

6. **Credential hygiene.** During initial setup, a GitHub personal access token was accidentally committed to a text file and pushed to a (briefly public) repository. GitHub's automated secret scanning detected and auto-revoked it. The incident prompted a standing rule for this project: credentials are only ever entered into the specific secure prompt/field requesting them (a terminal password prompt, a `.env` file, a masked panel input) — never into a document, chat, or anywhere that could be committed or logged.

   **Update, July 22, 2026 — Bitwarden adopted as the standing personal secrets vault.** The rule above covers where secrets live operationally (on the VPS, in `.env` files), but there was no durable personal backup of any of them until now — everything existed in exactly one place with no recovery path. Bitwarden (free tier) is now where every credential gets a canonical, durable copy the moment it's created or rotated: VPS root password, Twenty's `ENCRYPTION_KEY` and Postgres password, the freshly-rotated Twenty API key, and (in progress) Hermes's `.env` secrets, the BigQuery service account key, and external account logins (TrainingPeaks, GoDaddy, Stripe/Mercury, GitHub). Same day, SSH key-based auth (ED25519, no passphrase) replaced password login from Iván's Mac to the VPS — the root password itself is kept in Bitwarden purely as an emergency fallback, not for routine use. Deliberately not yet done, flagged as a follow-up: moving the Bitwarden master password itself out of Apple Passwords (a circular dependency — losing Apple ID access would lock out Bitwarden too) into memorized + physical paper backup, enabling Bitwarden's own 2FA and Emergency Access feature, and enabling 2FA on Hostinger's hPanel (the actual root of trust, since hPanel access alone is enough to reset the VPS root password).

7. **Agent reliability under complex, multi-step debugging (July 17, 2026).** While building the WhatsApp feedback-loop scripts, Hermes produced a string of unreliable output in one session: it misdiagnosed a working network path as a missing Tailscale install, wrote Python with broken indentation and missing logic while narrating that it had "completely transitioned the setup," Base64-encoded a credential with the stated goal of "bypassing security-redaction filters" (flagged and reversed immediately — plain-text storage was already the intended pattern for secrets on this box, e.g. `~/.hermes/.env`), and at one point requested to delete a script and create a new self-authored "skill" without being asked. Root cause judged to be the flash-tier Gemini model's known weaker performance on sustained agentic reasoning, compounded by a long session's accumulated context. Two standing changes came out of it: (a) for this class of task, verify Hermes's claims against literal command output or file contents rather than trusting its narration — several "fixed and confirmed" reports turned out to be wrong when checked directly; (b) new automation logic gets written once, by hand, as a tested and complete script, with Hermes's role narrowed to *calling* it correctly rather than writing or modifying it — this is the pattern behind both `twenty_followup_check.py` and `update_lead_status.py`. Consequence: the Twenty API key that was briefly Base64-obfuscated should be rotated as a precaution. **Done July 22, 2026** — new key generated in Twenty's settings, old key revoked, `n8n`'s Twenty API credential (HTTP Header Auth) updated to match, new key saved to Bitwarden.

8. **Google Cloud project silently closed over negligible billing (July 2026).** The `training-plan-analytics` project (personal `ivankoch87@gmail.com` account, hosts the TrainingPeaks plan-view pixel) stopped accepting requests around June 30–July 1 with zero notification. Cloud Console showed a red "account closed" banner, which read like a serious policy violation but traced back to a mundane cause: `billing is disabled for this project`, on a project running roughly $0.01–0.015/month of usage — almost certainly an automated abuse-detection false positive on a never-billed free-tier project rather than an actual violation. Diagnosed via Cloud Run's Metrics tab (requests flatlined exactly at the outage date) and Logs (explicit billing-disabled error on every request). Fixed by linking a new Cloud Billing account to the project — no appeal or rebuild needed, despite the alarming banner language. Real impact: 20 days of pixel data lost (Jun 30 – Jul 21); the BigQuery table held the full history back to June 2025 throughout, and was downloaded in full as a precaution before any fix was attempted. Standing lesson: don't take Google Cloud's account-status banners at face value — check the actual request logs first, since the underlying cause is often far more mundane (and far more fixable) than the banner implies. Aftermath (the VPS Postgres backup pipeline): `ai-infrastructure-documentation.md` §9.

## Website deploy-path failures (July 26–27, 2026)

Three consecutive failures after the Eleventy cutover, all with the same root cause: **the VPS held state the repo didn't control.**

**403 on every page (July 26, fixed).** The first run of the new deploy script published successfully and then the whole site returned `403 Forbidden`. Cause: the script built into a directory created by `mktemp -d`, which is mode `0700`. `rsync -a` preserves permissions and — with a trailing slash on the source — applies the *source directory's* mode to the destination, so the deploy rewrote `/var/www/triaperformance` from `755` (owned by Iván) to `0700 root:root`. Every file inside remained `644` and every subdirectory `755`, so `ls -la` of the contents looked completely healthy; the problem was the webroot directory itself, which Caddy (running as the `caddy` user) could no longer traverse.

Diagnosed with **`namei -l /var/www/triaperformance/index.html`**, which prints the permissions of every component along a path and surfaced the single bad line (`drwx------ root root triaperformance`) immediately. `journalctl -u caddy` was useless here — it showed only routine ACME/TLS maintenance, no request errors at all. Standing lesson: for a webserver permission fault, check the whole path with `namei -l` before reading logs; `ls -la` of the directory contents actively misleads in this failure mode.

Three fixes, all in `automation/deploy-website.sh`: `chmod 755` on the build directory before rsync (fixes the cause), `chmod -R a+rX` on the webroot after (fixes any inherited state), and a post-deploy loop that curls `/`, `/planes/running/` and `/members/login/` and prints the HTTP status of each — so this class of failure reports itself at deploy time rather than via a browser. Also fixed in the same pass: the script used `npm ci --omit=dev`, which skips devDependencies — and Eleventy is a devDependency, so the one package the script needs was never installed (npx was silently fetching it on the fly).

**Diverged branch (July 27, fixed).** The link checker was run on the VPS and its results committed there. `git commit` needs no credentials — only `git push` does — so the box acquired a commit it could never publish. The next deploy's `git pull --ff-only` hit a diverged branch and aborted before building. The site silently stopped updating, with the failure buried in `kb-sync.log`. Fixed by making the VPS a strict mirror: `git fetch` + `reset --hard origin/main` + `clean -fd`, which cannot diverge or conflict. Consequence, deliberate: **anything inside the VPS checkout is destroyed on every deploy.** Generated data must live outside it — hence `PLAN_LINK_STATUS`, an env var letting a cron write link-check results to `~/.hermes/plan_link_status.json` where the reset can't reach them.

**Stale live script (July 27, fixed).** `~/.hermes/deploy-website.sh` is a *copy* of the repo's `automation/deploy-website.sh`, so fixes to the script never reached the box, and a broken live script could not pull its own fix. Fixed by having the script copy itself forward at the **end** of a successful run — so a bad commit can't brick the deploy path, and the new version only takes effect once a run has proven it works. This required one final manual copy to bootstrap, since self-update code has to be in the running script to do anything.

**The invariant the fixes converge on: the VPS owns nothing.** It resets to origin, rebuilds from scratch into a temp directory, re-copies its own script, and writes generated data outside the checkout.

**A verification that lied.** The post-deploy check added after the 403 reported `FAIL 000000` on all paths of a site that was working perfectly. Two bugs: curl emits `000` via `-w` on failure *and* the `|| echo "000"` fallback appended a second one; and the check used `https://127.0.0.1` with a `Host:` header, but **Caddy routes TLS by SNI and curl sends no SNI for a bare IP address**, so the handshake failed before HTTP was ever spoken. Fixed with `--resolve triaperformance.com:443:127.0.0.1`, which keeps hostname, SNI and certificate consistent while connecting to loopback. Worth recording because a false-alarming verification is worse than none — it trains you to ignore the one signal meant to catch real breakage.

## Catalog facet filters never filtered anything (August 6, 2026)

Reported by Iván against the live storefront: checking a sport didn't narrow the plan grid, and the distance/enfoque options didn't respond to the sport selection either. Both symptoms, one cause — and the cause was not in the code that appeared to be at fault.

`catalog-filters.js` was correct and running the whole time. It read the checked boxes, computed OR-within-group / AND-across-groups exactly as designed, updated the result count, and set `hidden` on precisely the right cards. Every card that should have disappeared *was* flagged as hidden. Nothing disappeared.

**Root cause: `hidden` is a user-agent stylesheet rule.** `[hidden] { display: none }` lives in the browser's default stylesheet at the lowest specificity in the cascade, so *any* author rule that sets `display` on the same element beats it silently. `plan-page.css` set `display` on three of the four things the script hides:

| element hidden by the JS | competing author rule | result |
| --- | --- | --- |
| `.catalog-card` | `display: flex` | stayed visible |
| `.catalog-grid` | `display: grid` | stayed visible |
| `.facet-options label` | `display: flex` | stayed visible |
| `.catalog-empty` | *(none)* | worked — by accident |

The one element that behaved correctly did so only because nobody had styled it. Fix is three selectors — `.catalog-card[hidden]`, `.catalog-grid[hidden]`, `.facet-options label[hidden]` — restating `display: none` as an *author* rule. Specificity (0,2,0) vs (0,1,0), so it wins on the cascade without `!important`.

**The part Iván hadn't seen yet.** The four category pages (`/planes/running/`, `/triatlon/`, `/hyrox/`, `/bajar-de-peso/`) render the full 179-plan ES catalog server-side and rely entirely on a pre-checked box plus this same JS to narrow on load. With the bug, all four were serving the entire catalog: the HYROX page listed every swim, cycling and triathlon plan, 179 instead of 7. Those are the oldest, most-linked plan pages on the site and they are in the main nav. Post-fix, on-load counts are Running 85, Triatlón 30, HYROX 7, Bajar de Peso 19.

**Why it survived the July 30 build check.** That session verified the build the way a build gets verified — clean Eleventy run, correct page counts, right number of cards, data attributes present, no template-syntax leaks. All true, all passing, and all blind to this: the markup and the JS were both individually correct, and the defect only existed in the interaction between the script and a stylesheet neither check looked at. A static build check cannot catch a cascade bug. Nor can jsdom on its own — it models the DOM well but not the UA stylesheet, so `getComputedStyle` there would have shown `display: none` and confirmed a bug that was live on the site.

Verified in two parts, deliberately separated: jsdom for the filtering behaviour (14 assertions — sport filter, dependent distance facets, AND/OR semantics, reset, empty state), and a specificity calculation parsed from the real CSS for the cascade question, because that is the half jsdom cannot be trusted on.

**Standing lesson: never hide a styled element with the `hidden` attribute alone.** Either pair it with an author-level `[hidden] { display: none }` rule, or toggle a class. This is a silent failure by construction — the DOM says hidden, the accessibility tree says hidden, `element.hidden` returns `true`, and the pixels are still there. Any future tool or page that hides elements this way needs the author rule shipped alongside it.

**Mobile follow-up, same day.** With the filters finally working, the mobile layout underneath them turned out to be broken too: below 800px the sidebar column collapses, but `.facets` kept `position: sticky`, and on iOS Safari the pinned filter list painted on top of the scrolling card grid. Rather than chase sticky-inside-collapsed-grid behaviour across engines, the facets became a horizontal row of chips pinned under the nav, each opening a dropdown panel — Iván's own suggestion, and the pattern that removes the failure mode instead of patching it.

Two implementation notes worth keeping. **The panels are `position: fixed`, not `absolute`,** because the chip row is a horizontal scroller and `overflow-x: auto` computes `overflow-y` to `auto` as well — an absolutely-positioned panel would be clipped by its own parent. Fixed descendants escape ancestor overflow (nothing in the chain creates a containing block for them). **The sticky offsets are measured in JS,** not hardcoded: the nav's height varies by language and shifts again once webfonts land, so `--nav-h` and `--facets-bottom` are set from `offsetHeight` on load, resize and orientation change, with close-enough CSS fallbacks for the pre-script paint.

Deliberately not duplicated: the mobile UI reuses the same markup, the same checkboxes and the same `applyFilters()` as desktop. Only presentation changes, so there is exactly one source of filter state and no second set of inputs to drift. Verified with 36 assertions across both layouts (`matchMedia` stubbed per run to force each branch) — desktop regression, chip open/close/exclusivity, badge counts, scrim, reset, and the category-page presets still narrowing to 7 on `/planes/hyrox/`. **Still pending: Iván's real-device check.** jsdom has no layout engine, so nothing here proves how it looks on an actual iPhone — which is exactly the gap that produced this fix in the first place.

**Two bugs in the first mobile attempt (same day, found on a real iPhone).**

*Bug A — the chips did nothing.* The click handler fired, the class toggled, the panel opened. It was simply invisible, and every tap landed on the scrim. Cause: `.facets` is `position: sticky` **with a z-index**, which makes it a stacking context — so everything inside it, panels included, paints as a single layer at z-index 50 no matter what z-index the panel itself carries. The scrim was at 55, i.e. above the very panel it was meant to sit behind. It covered the dropdown and swallowed the taps.

The scrim was at 55 because the panels had been pushed to `position: fixed`, and that was pushed by making the chip row a horizontal scroller: `overflow-x: auto` computes `overflow-y` to `auto`, which would have clipped an absolutely-positioned panel. Each decision was locally correct and the chain ended somewhere broken. The fix removes the first link rather than patching the last: the chips **wrap** instead of scrolling, so there is no overflow, so the panels can be plain `position: absolute` against `.facets`, and the scrim drops to z-index 40 — below the bar, above the cards. If the labels need two rows, they get two rows.

The reasoning error worth naming: `position: fixed` does escape ancestor `overflow` clipping, which is what the earlier note claimed and is true. It does **not** escape an ancestor's stacking context, which is what actually mattered. Escaping clipping and escaping stacking are different questions, and only one of them was asked.

*Bug B — card text turned red mid-scroll.* `.catalog-card` is a bare `<a>` and this stylesheet never gave it link styling. `site.css` has no global `a` reset either — link styling there is scoped per component (`.logo`, `nav a`, `.card-links a`, `footer a`) — so the cards had been rendering with user-agent defaults all along: blue, underlined, and red while `:active`. On a touch screen `:active` fires on press and persists through a scroll that *starts* on a card, which is exactly the "only when I scroll while pressing a card" pattern Iván described. Fixed by stating colour and `text-decoration` across every link state, plus `-webkit-tap-highlight-color: transparent` and a deliberate `:active` border for press feedback.

Bug B had been live since the storefront shipped on July 30 and no automated check would ever have found it — it isn't a broken behaviour, it's a missing declaration that only looks wrong to a human eye on a touch device.

**Standing lesson, earned twice in one day: jsdom proves behaviour, never appearance.** It has no layout engine, no stacking model, no user-agent stylesheet and no `:active`. Every one of these three bugs — the `[hidden]` cascade, the scrim stacking context, and the unstyled anchor — passed clean automated checks and was found by a person looking at a phone. Static checks are worth keeping, but the real-device pass is not optional and must come before a catalog CSS change is called done.

**Third mobile attempt — and the tooling lesson that should have come first.**

Iván reported the chips still dead on an iPhone, with a grey flash on tap. Two remote guesses had already failed, so this round started by building a real browser instead of reasoning about one. Playwright's Chromium wouldn't launch in the sandbox (`libXdamage.so.1` missing, apt blocked by the egress proxy); the four symbols it needs are X11 Damage-extension calls that headless never makes, so a ~6-line C stub compiled with the system gcc satisfied the linker and Chromium came up. WebKit needs the full GTK stack and stayed out of reach — so Safari's engine was still never tested, which is stated plainly here rather than papered over.

Real Chromium at an iPhone 13 viewport found the bug in one run, and it was not exotic. The panel was anchored to the bar, and `position: sticky` only pins the bar once you have scrolled to it. With the page near the top the bar sat at y=605–752 in a 664px viewport, so the panel opened at **y=751 — 87px below the fold.** Invisible. Sweeping the scroll position made it unambiguous: broken at scrollY=0 and 200, fine from 400 down. Every earlier check had implicitly tested the scrolled state and declared victory.

The fix stops anchoring to the bar. On open, JS **moves** the panel into `.facet-portal`, a plain `<div>` appended to `<body>`, and returns it on close — so exactly one copy of every checkbox exists at all times and there is still no duplicated filter state. As a child of `<body>` the panel has no ancestor overflow, no ancestor stacking context, and — the part that matters for the untestable engine — no dependence on how a browser positions descendants of a `sticky` element. `--panel-top` is computed per open and clamped between the nav's bottom and half the viewport, so the panel is reachable wherever the bar happens to be. Because the open panel leaves the container, the delegated `change` listener moved to `document`.

Two more things only a rendered pixel could have shown:

- **The scroll lock ate the nav.** `overflow: hidden` on `<html>` while a panel is open looked correct in the DOM and passed every assertion — a screenshot showed the nav and the chip bar had vanished, because locking the scroll container stops `position: sticky` from working. The user lost the bar they were filtering with. Replaced by swallowing `touchmove` on the scrim, which blocks background scrolling without touching layout.
- **Phantom "0" badges on every inactive chip** — the `[hidden]` trap for the *fourth* time in one day, since `.facet-badge` sets `display: inline-flex`. Now covered by a broader author rule that also takes in `.facet-reset` and `.facet-scrim` before they bite too.

Also fixed while in there: the chip bar was 147px — three rows — which with the nav meant 34% of an iPhone screen was permanently chrome. Short mobile labels (`filterDistanceShort` etc. in `planUi.json`, ES/EN/PT), smaller chips, and a reset chip that only appears once something is filtered brought it to 95px and two rows, 27% including the nav.

**The lesson, and it is a tooling lesson, not a CSS one.** Four bugs in this feature — the `[hidden]` cascade, the scrim stacking context, the unstyled anchor, the off-fold panel — every one of them invisible to jsdom and every one of them caught in seconds by a real engine or a real screenshot. Two rounds were spent guessing at a browser from a distance and shipping the guesses to Iván to test. Standing rule from here: **for any change to rendered layout, stand up a real browser first and look at a screenshot, before proposing a fix.** The stub-library trick above makes that cheap, and `automation/` should grow a checked-in version of this harness rather than rebuilding it next time.
